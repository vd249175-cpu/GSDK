# 前置事实与模型研判

依赖规划必须同时尊重项目事实和模型事实。仅凭记忆选择模型或凭节点名称猜测项目状态，都可能生成无法执行的结构。

## 先确认语境

使用调用 `get_structure` 工具（默认深度 `depth: 1`）认识项目顶层，再围绕目标分支逐层查看结构，最后调用 `query_nodes` 查询当前决策需要的字段。由此判断项目规模、当前目标幕、资产沉淀情况和分镜是否已经具备。不要用全量展开或全局递归长字段查询代替这一步。

随后根据任务从导航中读取相关细节：上下文范围不清楚时阅读分层查询文档，镜头控制程度不清楚时阅读复杂度文档，准备写入层级时阅读工程结构文档。

## 核验当前模型契约

先调用 `list_generation_models` 查看当前可用模型，再用其 `modelId` 参数查询候选模型。重点确认：

- `mediaType` 是否与图片、视频或音频节点匹配。
- 模型接受纯文本、单帧、首尾帧、多参考还是音频驱动。
- `capabilities.references`、`capabilities.maxReferences` 和 `nativeAudio` 等引用能力。
- `parameters` 与 `defaults` 中允许的时长、分辨率、宽高比和其他参数。

静态模型表只能帮助提出候选，不能替代这次查询。模型不存在、引用超限或参数不合法时，应调整拓扑或候选模型，而不是把不兼容的结构写入项目。

## 形成并验证方案

把已确认的叙事需要、复杂度和模型硬约束共同转化为依赖结构，再用 `edit_node`、`batch_edit`、`write_markdown` 或 `run_logic` 落盘。完成后局部回读结构，并再次确认节点类型、引用数量和参数都符合所选模型。

用户需求过于宏观且不同选择会显著改变成本或控制程度时，先把关键取舍讲清楚并询问偏好；能够从项目事实安全推断的部分则继续推进。
