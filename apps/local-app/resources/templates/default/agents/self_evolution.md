# 提示词维护与自进化守则

这份文档用于规范 GraphVideo 体系中所有 Agent 认知文件与提示词的维护与自进化。目标不是无休止地堆叠规则，而是让核心人格保持稳定，让专业细节按需读取，让新增知识始终有唯一、清晰的权威归属。

---

## 1. 认知文件分层与内容归属

在新增、精简或重构提示词之前，必须先判断内容在认知体系中的层级：

| 文件 / 位置 | 角色与定位 | 修改约束 |
| :--- | :--- | :--- |
| **`AGENTS.md`** | **核心人格与最高准则**：角色的核心定位、创作品味与少数不可违反的最高行为准则。 | 只有核心职责或品味发生根本变化时才修改，保持极度克制。 |
| **`NAVIGATION.md`** | **工作导航中心**：用自然语言编写的任务地图。包含任务辨识维度、文档目录说明、常见阅读路径与无法确定时的回退方法。 | 新增或移除文档时同步更新；不承载具体操作步骤或长篇代码范例。 |
| **`../<公共文档>.md`** | **公共跨角色知识**：如 `project_knowledge.md`（项目目录、节点符号、数据流）或本自进化守则。 | 位于 `agents/` 根目录下，由所有 Agent 共同引用，避免各目录重复。 |
| **`details/<主题>.md`** | **任务细节与专业规范**：特定创作任务需要的边界、流程、判断标准、输出格式与核心范例。 | 围绕单一主题组织，保持自足与精确。 |

### 唯一事实源原则
- 现有文件已覆盖相同主题时，必须直接更新原文件，**严禁创建同义或重叠的入口文件**。
- 一项规则在全体系中只保留一个权威版本，其他位置仅通过链接或导航简要说明引用关系。

---

## 2. 工作导航 (`NAVIGATION.md`) 的编写规范

导航是 Agent 理解任务情境并选择文档的枢纽：

1. **使用自然语言地图**：导航应当像一张清晰的任务地图，通过自然语言描述情境与文档关系。**严禁使用 `when/do`、`&&`、`|`、`!` 或机械条件伪代码**代替自然语言判断。
2. **导航核心组成**：
   - **任务辨识**：从用户最终产物、项目阶段、改动范围与职责边界帮助 Agent 识别任务类型；
   - **文档目录**：每个条目说明该文档解决什么问题、何时必须加载、何时可以暂缓；
   - **常见阅读路径**：展示多份文档在典型工作流中的组合示例（作为参考，非机械死板流程）；
   - **回退策略**：当信息不足或方向不确定时的安全应对方法（如先查项目事实、先读职责边界、向用户确认）。

## 3. 文档头部元数据规范 (YAML Frontmatter)

所有 `details/*.md` 以及公共文档顶部必须包含标准 YAML 元数据：

```yaml
---
title: "文档标题"
description: "用一个完整句子说明这份文档解决什么问题。"
---
```

### 元数据契约要求
- **`title`**：简短、稳定、清晰，且**必须与正文的一级标题完全一致**。
- **`description`**：**单行、自足、具体**。用于 `list_agent_documents` 在不读取正文时直接生成文档库索引摘要。不得包含执行步骤，不得使用依赖上下文的代词（如“本规则”、“上述步骤”）。
- **字段值使用双引号**：避免标点符号被 YAML 解析器误判。

---

## 4. 提示词自进化与修改流程（严格审批模式）

当 Agent 需要学习用户偏好、更新自身规则或响应用户对提示词的调整要求时，必须严格执行以下流程：

```text
1. 现状调研与索引 (AGENTS.md / NAVIGATION.md / list_agent_documents)
   │
2. 规划修改范围 (明确清除、增添、合并的内容)
   │
3. 【强制】向用户提报方案，等待明确批准无论什么模式下都需要先得到用户批准才能修改文档。
   │
4. 执行落盘修改 (更新细节文档 / YAML 头部 / 同步 NAVIGATION.md)
   │
5. 闭环检查 (无死链 / 标题一致 / 无同义冗余)
```

### 强制审批红线
- **在修改任何提示词文件落盘前，必须先向用户说明明确的修改范围**（指明哪些内容需要清除、增添或合并，并附带简要理由与描述）。
- **未经用户明确批准，严禁擅自修改或写入提示词文件**。
- 获得批准后，遵循最小改动原则进行精准更新。
