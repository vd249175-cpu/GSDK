# 多 Agent 独立开发与运行协作指南

根目录 Bash 入口（`run.sh start/stop/status`）、v2 `runs/<name>/run.config.json` 与完整 Studio 桌面 run 已交付。测试覆盖真实 Node 切片、两个 Electron 前端并行、项目编辑后 SQLite 保存、场景自动关闭及清理失败重试。信号、启动中取消和旧插件目录收敛仍需继续验收，不能用发现文件隔离代替实际进程验证。实施顺序见[统一 run 实施计划](./unified-run-plan.md)。执行事实以源码、测试和[心智模型](./mental-model.md)为准。

## 1. 协作单位是任意命名的 run

协调者为每个 Agent 分配一个不重复的名称，例如 `alice`、`task-42`。该名称可以自由选择，分配后稳定使用，对应 `runs/<name>/`。名称不表示插件、业务分类或每次启动生成的实例 ID。

一个 run 是独立开发、运行和测试空间，具有自己的运行配置、开发源码、前端、后端宿主、权威图运行时和生成资源。同一个 run 可先运行片段，再修改配置运行完整程序。运行范围可以是单节点、插件片段、完整插件、跨插件组合或全部程序；范围不受插件目录边界限制。

多个 Agent 通过不同名称的 run 并行工作。同名 run 同时只允许一个活动运行；需要相同装配的并行副本时，分配另一个名称，并引用共享装配源码。内部控制凭证可以区分前后两次启动，但不能用随机实例目录替代固定的 run 目录。

## 2. 目标目录

```text
GVSDK/
├─ run.sh                         # Bash 统一入口：start / stop / status
├─ packages/
│  ├─ tooling/run/                # 配置、编排、隔离、测试和控制工具
│  ├─ rust/                       # 共用 Rust 内核实现
│  ├─ sdk/
│  ├─ frontend/                   # 共用前端底座
│  └─ desktop/                    # 共用桌面宿主
├─ app/
│  └─ plugins/                    # 已有插件源码和交付物
└─ runs/
   ├─ alice/                      # 任意分配的名称
   │  ├─ run.config.json          # 本 run 的运行与测试配置
   │  ├─ plugins/                 # 本 Agent 开发的普通插件
   │  ├─ frontend/                # 前端装配与服务绑定
   │  ├─ backend/                 # 后端宿主与 Adapter 装配
   │  ├─ graph/                   # 节点实例装配和因果输入
   │  ├─ scenarios/               # 场景输入与断言，可选
   │  └─ .generated/              # 不提交，本 run 独占
   │     ├─ frontend/             # 前端产物和缓存
   │     ├─ backend/              # 后端产物和缓存
   │     ├─ runtime/              # 进程身份、端点、凭证、配置快照
   │     ├─ data/                 # 数据库、用户数据、临时文件
   │     └─ logs/                 # 运行日志和场景报告
   └─ task-42/
      └─ ...
```

run 内的源码目录按实际需要创建；无用户操作需求的 run 可以不装配前端。存在前端时，必须使用该 run 自己的运行实例和连接配置。前后端装配可以引用共用入口，不要求复制平台代码或正式插件实现。

`runs/<name>/plugins/` 中的开发插件沿用相同 Manifest、公开 SDK、生命周期和 Node 命名空间规则。开发者不修改其他 Agent 或发布者拥有的插件目录。插件完成后由协调者将明确的制品或源码变更纳入集成，不通过运行工具自动搬移或改写正式插件。

## 3. 配置文件决定运行

启动必须显式指定该 run 的配置文件，不依赖当前工作目录、默认 Studio 装配或全局环境变量偷偷选择另一套图。配置中的相对路径以配置文件所在目录为基准解析。

v2 配置与 `packages/tooling/run/src/config.mjs` 分开描述以下内容：

| 配置部分 | 职责 |
| --- | --- |
| 版本与来源 | 配置版本、插件目录、公开装配入口和依赖 |
| 内核 | Rust 可执行文件、绑定参数、启动与关闭超时 |
| 前端 | 入口、Element 集合、连接绑定、监听参数、是否启用 |
| 后端 | 宿主入口、worker/provider 装配、Adapter 和物理能力 |
| 图装配 | 实际节点实例及构造依赖，切片边界的明确处理 |
| 因果输入 | 定向初始化、启动和关闭 Info，类型与 payload 校验 |
| 结算条件 | 就绪回执、在途工作屏障、关闭完成事实与超时 |
| 场景 | 可选输入、投影与边界断言、时钟及结束条件 |
| 资源 | 本 run 的生成目录、数据目录、端口和资源共享声明 |

运行工具必须在获得物理资源前检查配置和引用。配置引用受信任的模块入口，不以 `eval` 执行配置内容。凭证保存在本 run 的生成目录，不写入提交的配置文件。

启动后保存已解析的活动配置快照和资源身份。关闭以该次活动运行记录为准；运行中修改配置不能让 `stop` 误关另一个进程或遗留原来的资源。

## 4. Bash 启动与关闭

已交付的实际命令（`run.sh` 只做编排：校验→锁→空内核→装配→初始化→启停 Info→场景→关闭）：

```bash
bash ./run.sh start runs/alice/run.config.json
bash ./run.sh status runs/alice/run.config.json
bash ./run.sh stop runs/alice/run.config.json
```

Bash 直接启动并等待 Rust、后端 Node 与前端 Electron 进程。配置解析、协议 DTO 和断言由 `packages/tooling/run` 实现，工具只执行单阶段操作。无场景的 start 等待业务和前端 Ready 后返回，持续交互直到 stop；有场景的 start 等待报告及完整关闭后返回，失败为非零退出码。stop 认证活动快照中的控制接口，等待原始关闭 Info、业务结算、租约释放、evict/dispose 和子进程退出；清理失败保留锁与凭证以供重试。

启动顺序：

```text
校验配置并取得本 run 的运行锁
→ 准备独立产物和物理资源
→ 启动空 Rust 内核，确认内核端点就绪
→ 启动配置中的后端、前端宿主，确认可用
→ 显式推入节点
→ 定向注入初始化 Info，确认初始化结算
→ 定向注入启动 Info，确认业务就绪
→ 正常交互，或执行配置中的场景和断言
```

关闭顺序：

```text
限制新业务入口，保留停机控制与必要 Observation
→ 注入关闭 Info
→ 等待业务准备、在途工作和持久化结算
→ 停止观察来源
→ 推出节点，并确认 handler、销毁钩子及相关 Effect 已结算
→ 显式关闭空 Rust 内核，并确认内核进程退出
→ 停止前后端宿主及剩余服务
→ 更新运行记录，释放本 run 的运行锁
```

内核启停、拓扑准入/推出、Info 注入是独立命令，`run.sh` 组合它们。前后端进程提前存在不代表业务已经启动；后端在节点推出完成前不能提前终止。关闭窗口不自动等同于关闭整个 run，图内窗口关闭仍由业务协议决定。

`stop` 可从另一终端调用（读活动快照，运行中改配置不改变关闭对象）；重复停止与已停止成功返回。启动中断清理已获得资源，尚未启动的业务不被假定已完成业务退出。`force-stop` 与 Ctrl+C/TERM 同一停机编排尚未交付，不作为正常关闭的替代。控制工具不能仅凭陈旧 PID 杀进程，必须核对活动运行的进程身份与端点所有权。

业务保存失败或停机超时必须报告失败、保留诊断与控制入口，不冒充干净退出（`scenario` 报告保留断言证据与清理结果，原始失败退出码不被清理成功覆盖）。
## 5. 并行资源与源码所有权

每个 run 独立拥有 Rust 规则空间、前端实例、后端宿主、端口、发现文件、Electron 用户数据及单实例身份、SQLite/文件锁、日志、测试缓存和可写构建产物。默认端口动态分配；显式端口冲突应报错，不能悄悄连接其他 run。

共用 SDK、Rust 制品和正式插件可以作为只读输入。运行与测试不覆盖共用 `.node` 文件，不写回插件源码旁的生成 JS，不删除共用依赖目录。构建共用平台制品由协调者串行完成，或写入任务独立输出目录。

物理项目数据默认使用本 run 的目录或独立副本。需要共享外部资源时，明确声明访问方式和并发约束；目录分开不意味着远端任务、设备或同一个数据库自动隔离。

协调者分配名称时同时登记 Agent、任务范围、可修改路径和需要协调的共享文件。Agent 默认只修改自己 run 下的源码；改 SDK、正式应用或其他共享文件时，先由协调者安排明确的文件所有权。

同一个 Git 工作树中的目录隔离不隔离索引和提交。共享工作树时由一个协调者负责暂存和集成提交，各 Agent 提供路径清单与验证结果；禁止并发使用全量暂存、重置或清理。独立分支/worktree 可隔离版本操作，但不能替代 run 对物理资源的隔离。

## 6. 任意图片段与初始化边界

run 配置使用 `version: 2`。`graph.instances` 显式声明 `kind/id/factory/params/bindings`；单节点工厂收到实际 `nodeId`，图工厂通过 `nodeIdFor(localId)` 分配本实例地址。重复实例或 Node ID 会报错，不会自动合并 Owner。Studio 的 `bindings` 可覆盖命名通信目标；静态分析从实际实例的目标字段读取证据。

运行配置显式选择真实节点实例，不能先装配整图再隐藏未选择节点。切片可以跨越插件目录，但插件协作必须遵守公开契约，不能相对导入其他插件的私有实现。

被切断的交换面需要明确选择真实参与者、Collector、测试 WorldNode/Adapter，或允许并断言的 dropped Info。不得静默补齐整个应用，不复制框外 Owner State。静态切片分析用于核对边界，不自动替代实际运行装配。

环境连接信息、资源路径、目标绑定和 Adapter 属于宿主或构造装配；初始化 Info 携带 Owner 应接受的业务初始事实。不要把 Node ID、函数、绝对物理路径或另一份业务投影塞进业务 State。需要迁出的硬编码逐项判定归属，不能统称为无限扩展的配置袋。

所有 Node 间通信仍为 `ctx.send(info, targetNodeId)`，发送的 `Info.type` 和目标证据必须可证明。前端绑定当前 run 的 Projection 和经过授权的命令入口；测试控制面不授予普通前端任意 Info 注入或 State 干预权限。观察与执行 WorldNode 保持物理分离。

## 7. 测试与整程序使用同一运行机制

测试是在同一次真实运行上增加场景输入、断言和结束条件。它使用同一配置解析、节点装配、Rust 调度、初始化和停机机制；没有第二套测试专用应用启动器。

场景失败仍执行有边界的正常清理，保留失败原因、资源清理结果和非零退出状态。持续观察的图以明确回执和屏障判断就绪及结束，不能把瞬间队列为空当成业务完成。单 Node 单测仍可使用已有 `createTestRuntime`，但它不替代真实 Rust 运行验收。

完整 Studio 使用 `bash ./run.sh start runs/studio/run.config.json`，关闭使用同配置的 stop。`npm start` 拒绝隐式装配，`start:legacy-electron` 已移除。其他命名 run 可以引用同一工厂和前端宿主，以各自 namespace、配置和物理资源运行。

## 8. 任务交付

Agent 交付应包含自己的 run 配置、源码变更、运行范围、边界说明、场景和测试结果，并确认本 run 已停止、没有遗留进程或监听。失败诊断可以保留，但凭证和生成产物不能提交。

协调者用另一命名 run 进行集成，验证片段与完整程序。集成不得借用仍在运行的 Agent 规则空间，不通过拷贝 State 合并业务事实，也不让某个 Agent 的目录成为正式程序的隐式运行依赖。
