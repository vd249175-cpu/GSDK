# Bash 配置驱动的统一 run 实施计划

本文是用户确认方向后的目标实施计划，尚未实现，不是当前 API 或启动命令说明。协作约束见[多 Agent 独立开发与运行协作指南](./multi-agent-run-guide.md)。完成各阶段后再将已实现事实同步至当前参考文档。

## 1. 最终目标与完成边界

根目录提供 Bash 入口，显式读取 `runs/<任意名称>/run.config.json`，完成正常程序、任意图片段和场景测试的启动、运行与关闭。每个 Agent 拥有独立命名目录及前端、后端、图运行时和物理资源。

完整 Studio 必须迁入新的 run；旧启动方式不作为最终的并行选项保留。只添加 Agent 测试入口、只包一层 npm 命令、或只新增配置而继续由 Electron 持有内核生命周期，均不算完成。

采用现有 Rust daemon 作为独立进程宿主，复用唯一的 Rust 调度 crate。各 run 拥有自己的 daemon 进程；不新增 TS 生产调度器，也不在同一 run 内同时维护 N-API 图与 daemon 图的两份权威 State。JS/Python SDK 是同一协议的适配。

## 2. 现有基础与缺口

| 已有基础 | 本计划需要完成的缺口 |
| --- | --- |
| Rust daemon 的 admit/evict、worker/provider 租约、Info 与 shutdown 协议 | Bash 独立启停、进程身份与命名 run 控制 |
| 应用配置支持任意插件目录 | 不依赖完整插件的实例装配及 run 配置校验 |
| JS/Python daemon 客户端与 Node/Effect 接入 | Studio 真实 Node、Adapter、前端与生命周期的独立宿主接入 |
| Studio 关闭 Info、落盘与节点清理 | 将流程迁到 run 控制面，不让 Electron 退出决定内核寿命 |
| 真实 Node 与 Adapter 的针对性测试 | 同一真实 run 上的场景、断言、自动关闭 |
| 各包独立安装与构建 | run 独立产物、缓存、用户数据与资源发现 |

已知共享资源包括固定遥测端口、用户级 Agent discovery、默认 Electron 用户数据及单实例身份、共享 Vite 缓存和源码旁的生成 JS。它们需要逐项改为当前 run 的显式参数与输出路径。

## 3. 阶段一：配置协议和目录所有权

先定义版本化运行配置、路径解析、模块入口契约、完整运行与无前端片段的最小配置。配置字段分别表达内核、宿主、拓扑、因果输入、场景和结算条件。

在获得资源前校验插件身份、实际实例 ID 唯一性、初始化 payload、公开命令入口、选择范围和切口处理。名称来自目录，不生成随机实例目录。运行锁只允许同名 run 存在一份活动运行。

建立 `runs/` 模板与 `.generated/` 忽略规则。启动后保存解析后的配置快照；控制命令定位本次活动运行，配置变更在下一次启动生效。

验收：任意命名的两个配置能独立解析；从其他工作目录使用同一绝对配置路径得到相同装配；非法配置在启动任何进程前失败；场景可省略；同名重复启动不会创建第二份图。

## 4. 阶段二：Bash 编排与独立控制

实现根目录 `run.sh` 和工具层的 kernel、host、topology、info、verify 独立操作。Bash 控制流程，专用工具处理结构化配置与协议。Windows 使用 Git Bash/WSL 的路径边界需明确验证，不能混淆 Windows 可执行文件路径和 Linux 路径。

实现 start、stop、status，控制进程身份、运行锁、就绪回执、阶段日志和结构化退出结果。支持从另一终端停止、启动中停止、重复停止、Ctrl+C/TERM 和明确的强制终止。长驻控制组件跟踪进程与阶段，使启动脚本退出后仍可正确停机。

控制记录不能只保存 PID；核对进程身份与本 run 的端点所有权，处理陈旧记录和异常退出。正常 stop 等待所有阶段结果，启动失败按已获得资源清理，默认不全局杀进程。强制终止保留未完成阶段。

验收：空内核可独立启动和关闭；关闭确认后监听和进程均退出；同名重启可用；一个 run 的 stop 不触及另一个 run；被拒绝或失败的控制请求不会把运行记录改成成功。

## 5. 阶段三：前后端与物理资源隔离

前端、后端和图运行时由配置分别启动与绑定。前端只消费当前 run 的 Projection 和固定命令接口；后端运行 Node handler、Observation 来源和 Effect provider。一个 run 内共享一份权威图，不按前后端各建一份 State。

构建产物、测试缓存、Electron 用户数据、单实例身份、Agent discovery、遥测端点、项目数据和日志落入本 run 的资源范围。共用平台制品只读；并发平台构建另设所有权与独立输出，不能覆盖其他运行加载中的制品。

修改构建工具的输出参数，不向源码旁生成 JS；读取当前配置选定入口，避免旧生成产物遮蔽 TS 源码。停止和清理只操作本 run 拥有的资源；数据默认保留，主动清理数据使用独立明确操作。

验收：两个 run 同时拥有各自的前端、后端与 daemon；端口、缓存和 discovery 不互相覆盖；Electron 第二个 run 不被第一个的单实例锁吞掉；数据与日志互不串用。

## 6. 阶段四：真实 Node 装配与初始化

适配现有 Node 工厂到 daemon worker 执行边界，确认挂载、Context、State 编解码、错误 Info、generation 和 dispose 的真实行为。Adapter 通过独立 provider/宿主能力接入；纯领域 Node 保持零 I/O。

逐项盘点硬编码信息：进程与网络参数移至宿主配置；实际目标绑定与实例身份移至构造装配；业务初始事实通过定向初始化 Info 接受。Info.type 与实际目标的因果证据必须保留，不能用全局路由表掩盖发送点。

图装配接受明确实例集合，直接构造选择范围，不先执行完整插件工厂再丢弃未选择实例。正式插件提供公开装配契约，片段运行不依赖私有实现。切口使用明确参与者、Collector 或可验证的丢弃行为。

推出时先密封投递，等待当前 handler，再断代、丢弃 backlog、使租约失效并等待本地 dispose。daemon evict 不能被误认为已替 worker 完成销毁；必须增加外层 worker 清理确认。失败与超时不能报告已停止，不能默认重放跨 generation 消息或迁移 State。

验收：运行单 Node、完整插件和跨插件片段；不创建未选择实例；初始化先于业务启动；异常以 Info 流通；节点推出完成前没有活跃 handler/Effect 或未确认清理。

## 7. 阶段五：运行与场景测试共用生命周期

场景定义输入、期望 Projection/边界 Info/Effect、时钟、结算屏障和结束条件。场景执行器使用同一真实 run 控制面，不能自建第二套生产装配或改用 TS Oracle 冒充 Rust 验收。

场景成功和失败都进入同一关闭流程，保存断言与清理结果。测试异常和清理异常同时发生时保留两者；退出码不能掩盖原始失败。持续观察图通过明确协议暂停周期来源并结算在途工作，不无限等待整图静默。

验收：同一配置无场景时正常交互，有场景时自动注入、断言、结束；成功、断言失败、外部 Effect 失败和超时均得到确定的报告与资源状态。已有单 Node Vitest 测试继续作为局部验证工具。

## 8. 阶段六：整个 Studio 迁入新 run

建立一个协调者命名的正式整程序 run，例如 `runs/main/`。`main` 只是示例名称，没有内核特权；它通过配置装配全部所需能力，与 Agent run 使用同一入口。

迁出 Electron main 中的内核创建、插件隐式装配和全局运行参数。Electron 承担配置中的前端宿主与必要窗口物理能力，Rust daemon 独立拥有内核寿命，后端通过协议执行真实 Studio Node。

将项目服务、生成任务、持久化、窗口 Effect/Observation、Projection、IPC、Agent 控制及遥测绑定到当前 run。图内业务关闭协议负责保存与窗口处理，外层 run 负责推出、内核关闭和进程退出。必须验证传输变为异步后，不破坏现有顺序、取消、单飞或错误处理。

场景验证当前 Studio 的完整项目数据保存，保留标题未变化的元数据和保留记录，失败事务回滚。业务失败时保持可诊断和可重试的停机控制；不能由 Electron 先退出导致 provider 消失，再声称内核优雅关闭。

替换用户文档中的正常应用启动入口；清除旧的 npm 应用 start/prestart 路径和直接 Electron 自启动装配。各包的依赖安装、类型检查、底层构建与单测仍可独立执行，不能成为绕过 run 的另一套整程序启动方式。

验收：只用新 Bash 入口启动并正常使用整个 Studio；从另一终端正常 stop，按顺序完成保存、推出、Rust 退出和前后端停止；完整程序与至少两个 Agent run 并行，无资源冲突。旧整程序启动方式不再作为推荐或实际权威入口。

## 9. 阶段七：多 Agent 演练与文档收敛

协调者分配两个任意命名目录与明确文件所有权。一个 Agent 开发新插件，另一个运行跨插件片段和场景，同时正式 run 正常运行整程序。分别停止、重启，并集成公开契约或源码变更。

记录每个 run 的配置、选择范围、端点、资源路径、场景结果与关闭证据，验证不会误读其他 run 的 Projection、操作其他数据或关闭其他进程。

同步 mental-model、SDK 心智模型、目录边界、测试指南、桌面 README、应用生命周期及根 AGENTS 指引。当前参考文档只写实际通过验收的入口和边界；计划中的未完成项保持明确标记，不提前声称迁移完成。

验收：清理本次活动进程后，源码工作树只留下预期配置与代码，凭证和生成产物被忽略；团队能够仅凭协作指南分配、启动、测试、停止和交付一个 run。

## 10. 实施与验证原则

每阶段先补最小复现或验收场景，再实现并小步提交。优先局部验证，代码改动按仓库要求完成 desktop 与 JS SDK 类型检查，针对性 Vitest 使用 `--silent`；Rust 改动运行对应 crate 测试，跨语言协议变化同步共同契约与镜像 SDK。

| 关键验收 | 必须证明 |
| --- | --- |
| 并行 | 至少三个命名 run 的前端、后端、图和数据隔离 |
| 独立命令 | 启停内核不隐式装配或注入业务，装配不隐式启动业务 |
| 切片 | 只创建选定实例，交换面明确且可断言 |
| 正常关闭 | 业务结算后才推出，清理确认后才关内核，最后停止宿主 |
| 故障关闭 | 保存失败、挂起 handler、provider 断开不冒充干净退出 |
| 控制身份 | 配置被修改、PID 陈旧、重复 start/stop 不误操作其他运行 |
| 测试一致 | 场景与正常运行共用实际装配及 Rust 内核 |
| 整程序替换 | Studio 正常运行走新 run，旧启动路径退出使用 |

本轮任务只交付协作指南和实施计划，不创建运行脚本、不更改生产启动链路，也不将目标命令标记为已可用。
